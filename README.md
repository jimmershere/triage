# Triage Command Center

Triage is an EDI/X12 claim operations application with a FastAPI backend, Python worker pipeline, Go frontend/RBAC services, PostgreSQL, RabbitMQ, and a static operations UI. It supports file ingest, validation, acknowledgement capture, routing/tier execution, partner configuration, Claimtrace lineage, and dashboard workflows for operators and executives.

## What is in this repository

- `api/` — FastAPI service for ingest, jobs, admin users, partners, command-center metrics, Turbo validation routes, and Claimtrace routes.
- `worker_py/` — Python worker, X12/EDIFACT translators, SNIP validation, CMS scrubbing, FHIR mapping, routing, tier execution, and benchmark tools.
- `claimtrace/` — deterministic claim identity, correlation metadata, append-only journal primitives, Merkle proofs, and lineage projection helpers.
- `frontend_go/` — Go static-site server and reverse proxy for the public UI, API proxying, OAuth/RBAC integration, and security headers.
- `rbac_proxy/` — lightweight local oauth2-proxy-compatible login service for development and demos.
- `frontend_go/public/` — HTML/CSS/JS pages for Command Center, Ingest, Import Detail, Claims Portal, Claimtrace, Mapping, Edits, Partners, Admin, and reference pages.
- `samples/` and `demo-data/` — small and required test fixtures. Large generated benchmark fixtures are intentionally ignored and regenerated by the benchmark runner.

## Quick start with Docker Compose

1. Copy the example environment file and rotate placeholders before shared use:

```bash
cp .env.example .env
```

- `TRIAGE_SHARED_SECRET` must match across `api`, `frontend_go`, and `rbac` services.
- `TRIAGE_SESSION_SECRET` signs local RBAC sessions.
- `RMQ_*` and `RABBITMQ_URL` should match the RabbitMQ credentials in compose.
- The documented `3wm078uu` sample passwords are for local development only. Do not deploy them to shared environments.

2. Start the stack:

```bash
docker compose up --build
```

Default ports:

- Frontend UI: http://localhost:8080
- API docs: http://localhost:8000/docs
- RBAC login service: http://localhost:4180
- PostgreSQL: `localhost:15432` (db `edi`, user `edi`, password `edi` in the compose sample)
- RabbitMQ management UI: http://localhost:35672 (`ediapp` / `3wm078uu` in the compose sample)

3. Ingest a file from the UI at http://localhost:8080/ingest.html or call the API with the configured shared secret:

```bash
curl -X POST "http://localhost:8000/ingest" \
  -H "X-TRIAGE-SECRET: $TRIAGE_SHARED_SECRET" \
  -F "file=@samples/x12_837_small.txt" \
  -F "uploaded_by=demo" \
  -F "trading_partner_id=DEMO-PAYER"
```

## Native local stack

If PostgreSQL and RabbitMQ are already running on the host, use:

```bash
bash scripts/run-local-stack.sh
```

The script builds/runs the Go frontend, RBAC proxy, FastAPI API, and Python worker, using `.env.localhost` by default or `TRIAGE_ENV_FILE=/path/to/env` when set. Stop it with:

```bash
bash scripts/stop-local-stack.sh
```

## Claimtrace

Claimtrace is enabled by default for ingested files. During ingest, Triage creates a deterministic claim identity and a DB-backed trace record in `claimtrace_claim`, then appends trace events in `claimtrace_event`. The Claimtrace dashboard at `/claimtrace.html` supports searching by trading partner, submitter, claim ID, claim hash ID, and action state. Users can review identity, timeline, recommendations, and mark claims for repair, deletion, review, or release.

Implementation entry points:

- `api/claimtrace_service.py` — DB-backed persistence and dashboard helpers.
- `api/claimtrace_routes.py` — HTTP routes under `/claimtrace`.
- `claimtrace/` — identity, correlation, journal, Merkle, and lineage primitives.
- `frontend_go/public/claimtrace.html` and `frontend_go/public/static/js/claimtrace.js` — web dashboard.
- `migrations/001_journal.sql` — optional SQL bootstrap for the same tables used by the service.

Claimtrace tests run separately from the worker test suite:

```bash
bash scripts/run_e2e.sh
```

Set `CLAIMTRACE_APPLY_SQL=1` if you want that script to apply `migrations/001_journal.sql` before tests in an environment with `psql` available.

## Turbo validation and processing engines

The `/turbo/*` HTTP routes expose the Python validation/scrubbing/FHIR pipeline through `api/turbo_routes.py` and `worker_py/turbo_pipeline.py`.

Key modules:

- `worker_py/validation/` — SNIP-style validation for 837, 835, 270/271, 276/277, and related acknowledgement helpers.
- `worker_py/scrubbing/` — CMS-style payment/edit checks.
- `worker_py/fhir/` — FHIR R4 resources and X12/FHIR mapping helpers.
- `worker_py/routing_engine.py`, `tier_executor.py`, `tier1_assist.py`, and `tier2_swarm.py` — routing and tiered execution.

Representative routes:

- `GET /turbo/capability`
- `POST /turbo/validate`
- `POST /turbo/pipeline`
- `POST /turbo/fhir/from-x12`
- `POST /turbo/fhir/Claim/$submit`

## UI enhancements and support assistant

The frontend includes a daily operations guide injected by `frontend_go/public/static/js/site-enhancements.js`. It adds two EDI/X12/medical-claim graphics per page, rotates seven page-specific tips on a daily cycle, and applies subtle rotating panel tint/focus styles across the site.

The “Trish” support widget uses `frontend_go/public/static/js/support_config.js`. Replace the placeholder support email/phone values with deployment-specific contact points before production.

## Authentication and authorization

- The Go frontend proxies protected backend calls and injects `X-TRIAGE-SECRET` server-side. The shared secret is no longer emitted to browser JavaScript.
- The local `rbac_proxy/` service provides a lightweight oauth2-proxy-compatible login flow for development.
- Pages and controls use `frontend_go/public/static/js/auth_config.js` and `authz.js` for role-aware UI behavior.
- LDAP is optional. The default browser config marks LDAP disabled until a deployment explicitly wires a directory.

Local sample credentials such as `admin / 3wm078uu`, RabbitMQ `ediapp / 3wm078uu`, and LDAP sample passwords are local-development defaults only. Rotate `TRIAGE_BOOTSTRAP_ADMIN_HASH`, `TRIAGE_SHARED_SECRET`, `TRIAGE_SESSION_SECRET`, `RMQ_PASS`, `LDAP_ADMIN_PASSWORD`, and `LDAP_CONFIG_PASSWORD` before any shared deployment.

## Optional X12 CMS authenticity harness

`worker_py/tools_x12_cms_harness.py` parses 837 professional claim payloads, checks focused implementation-guide rules, and projects claims into CMS-friendly JSON. It always works with committed samples; when an optional licensed X222 research bundle is present in the expected `docs/turbohedi/x222-005010/` location, reports include paths to that material. Tests intentionally skip the bundle-specific assertion when it is absent.

Run:

```bash
python3 worker_py/tools_x12_cms_harness.py samples/x12_837_large_valid.x12 --pretty
python3 -m unittest worker_py/test_x12_cms_harness.py
```

## Optional bots translator

The worker auto-detects the optional `bots` EDI translator. To enable it in a local virtualenv or derivative worker image:

```bash
pip install "bots==3.2.0"
```

When present, the worker can use the `bots-edifact` adapter instead of the fallback EDIFACT parser. Use the translator helper to inspect active translators:

```bash
python -m worker_py.translators
python -m worker_py.translators samples/837.edi --json
```

## Security notes

- Browser clients must not receive backend shared secrets. Keep `TRIAGE_SHARED_SECRET` server-side only.
- Direct API write/operations calls require `X-TRIAGE-SECRET` when `TRIAGE_SHARED_SECRET` is configured.
- Store production X12 payloads in durable object storage and enqueue pointers/checksums if payload volume or retention requirements grow beyond the starter DB-backed flow.
- Rotate all sample credentials and secrets before any shared or production deployment.
- Keep `.env`, generated benchmark files, scratch notes, backup originals, and Python bytecode out of version control.
